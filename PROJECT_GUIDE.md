# Project Guide: Contract Generator Telegram Bot

Этот документ является основным источником информации об архитектуре, интерфейсах и правилах разработки проекта. Перед внесением любых изменений в проект необходимо сверяться с этим документом.

## 1. Архитектура проекта

Проект построен по модульной архитектуре с четким разделением слоев (Clean Architecture).

### Структура каталогов

- `src/main.py` — Точка входа в приложение. Инициализирует конфигурацию, зависимости и запускает Telegram-бота.
- `src/config/` — Управление конфигурацией. Загружает `.yaml` файлы и `.env`.
- `src/interfaces/telegram/` — Слой взаимодействия с пользователем. Обработчики команд, кнопок и FSM бота (например, `offers.py`, `schedule.py`, `generation.py`).
- `src/services/` — Внешние интеграции и специфичные бизнес-движки:
  - `offers/` — Offers Engine. Загружает и обрабатывает данные по ставкам из Google Sheets.
  - `schedule_tracker/` — Schedule Tracker. Анализирует расписание, ищет изменения (Diff Engine) и рассылает уведомления.
  - `google/` — Обертки для Google API (Drive, Sheets).
  - `bitrix/` — Взаимодействие с Bitrix24 REST API.
- `src/core/` — Основное ядро генерации договоров (`contract_engine.py`). Координация парсинга, обработки полей и рендеринга.
- `src/parsers/` — Извлечение данных из сырого текста.
- `tests/` — Юнит-тесты и интеграционные тесты для всех модулей.

### Жизненный цикл бота и порядок запуска

1. Загрузка конфигурации через `SettingsLoader`.
2. Настройка логгирования (`LoggingSetup`).
3. Инициализация внешних клиентов (Google Drive/Sheets через `GoogleAuth`, BitrixAPI).
4. Инициализация сервисов (`OffersLoader`, `ScheduleRepository` и т.д.).
5. Сборка `ApplicationComposition` (Dependency Injection) в `src/main.py`.
6. Запуск Telegram-поллинга (`run_polling`).

## 2. Публичные интерфейсы

Запрещается угадывать названия методов. Используйте только подтвержденные публичные контракты.

### `GoogleAuth` (`src/services/google/auth.py`)
- **Назначение**: Авторизация и создание клиентов Google API.
- **Публичные методы**:
  - `create_drive_client()` -> `Resource`
  - `create_sheets_client()` -> `Resource`
- **Параметры инициализации**: `config` (объект `AppConfig`).

### `ContractEngine` (`src/core/contract_engine.py`)
- **Назначение**: Главный координатор создания документов (DOCX/PDF).
- **Публичные методы**:
  - `generate(request: ContractRequest)` -> `ContractResult`

### `OffersService` (`src/services/offers/service.py`)
- **Назначение**: Управление кэшем и поиск городов в каталоге вакансий.
- **Публичные методы**:
  - `find_city(query_text: str) -> Tuple[Optional[CityOffers], List[CityOffers]]`
  - `refresh_catalog_if_needed() -> None`

### `ScheduleTracker` (`src/services/schedule_tracker/tracker.py`)
- **Назначение**: Поиск изменений в расписании (Diff) и их сохранение.
- **Публичные методы**:
  - `poll_and_notify(bot, recipients: list[int])`

### `BitrixAPI` (`src/services/bitrix/api.py`)
- **Назначение**: HTTP-взаимодействие с Bitrix24.
- **Публичные методы**:
  - `call_method(method: str, params: dict) -> dict`

## 3. Конфигурация

- **Расположение**: `config/settings.yaml` и `config/templates.yaml`. Чувствительные данные (ключи, токены) — в `.env`.
- **Загрузчик**: `src.services.config.settings_loader.SettingsLoader`.
- **Используемые секции**: `logging`, `paths`, `telegram`, `google`, `schedule` (периоды опроса, ID таблиц), `offers` (интервалы обновления), `bitrix`.
- **Правило**: Перед добавлением новой переменной окружения или настройки, проверьте секции в `AppConfig`. Не плодите дублирующиеся параметры конфигурации.

## 4. Структура моделей

Основные доменные модели проекта, реализованные через `@dataclass`. Перед добавлением полей убедитесь в их необходимости.

### Отдел Offers (`src/services/offers/models.py`)
- `Offer`: Модель одной вакансии в городе.
  - Поля: `search_name` (чистое имя для поиска), `display_name` (имя для отображения без лишних тегов), `job_type`, `legal_entity`, `rate_1`, `rate_2`, `rate_3`, `city_note` (примечание в скобках), `additional_info`.
- `CityOffers`: Группировка вакансий по городу (`search_name`, `display_name`, `offers`).
- `JobType`: Enum (`VELO`, `ELECTRO`, `VAHTA`).

### Отдел Schedule Tracker (`src/services/schedule_tracker/models.py`)
- `ScheduleRow`: Одна запись расписания (город, фио, статус и т.д.).
- `DiffResult`: Разница между новым состоянием и старым (новые, измененные, удаленные записи).

### Отдел Contract Engine (`src/core/contract_engine.py`)
- `ContractRequest`: Входные данные (проект, вакансия, текст, пути вывода).
- `ContractResult`: Результат генерации (пути файлов, ошибки, статистика).

## 5. Используемые сервисы

- **Google Drive**: Получение шаблонов DOCX (`TemplateCache`).
- **Google Sheets**: Чтение баз данных Offers и Schedule.
- **Bitrix24**: Получение данных контактов (гражданство, возраст) через REST API (вебхуки).
- **SQLite**: Локальная база (`schedule_state.db`) для хранения предыдущего состояния расписания и вычисления Diff.
- **Telegram**: Взаимодействие с HR-менеджерами через `aiogram`.
- **LibreOffice**: Используется локально (`soffice --headless`) для конвертации DOCX в PDF.

---

## 6. Offers Engine (Каталог вакансий)

- **Источник**: Исключительно **один лист** "Самокат" (Spreadsheet: `your_offers_sheet_id`, gid: `0`).
- **Нормализация городов**:
  - `search_name`: приводится к нижнему регистру, очищается от служебных меток (ВАХТА, прием девушек...).
  - `display_name`: очищенное имя с заглавной буквы.
  - `city_note`: содержимое скобок (выводится отдельно в интерфейсе).
- **Формат Callback**: Строго без мусора (`off_job:{search_name}:velo`). Запрещено использовать кириллические спецтеги в колбэках.
- **Вахта**: Маркер Вахты проверяется по наличию слова "вахта" в названии города или в поле "Тип". Выносится как отдельный `JobType.VAHTA`.

---

## 7. Contract Engine

- **Жизненный цикл**:
  1. `parse()` — парсинг сырого текста (ФИО, телефон).
  2. `process()` — обогащение полей (в т.ч. через Bitrix, склонение ФИО, подстановка дат).
  3. Поиск шаблона в `TemplateCache`.
  4. Рендеринг `.docx` через библиотеку `python-docx` / `docxtpl`.
  5. `create_pdf_converter()` — конвертация в PDF.

---

## 8. Schedule Tracker

- **Принцип работы**: Файловый поллер (`SchedulePoller`) регулярно читает Google Sheet.
- **Diff Engine**: При каждом чтении данные сверяются с `ScheduleRepository` (SQLite). Разница (`DiffResult`) используется для формирования уведомлений.
- Уведомления отправляются только `authorized_users` в определенные часы (`notification_start_time` - `notification_end_time`).

---

## 9. Bitrix24

- **Методы API**: `crm.contact.list`, `crm.deal.list`, `crm.contact.get`.
- **Пользовательские поля (UF)**: Хранят гражданство, возраст, статус и другие нестандартные данные.
- При получении контакта по телефону обязательно проверяются дубликаты.

## 10. Правила разработки

### Обязательный чек-лист перед написанием кода:
1. Проверить существующую архитектуру в `PROJECT_GUIDE.md`.
2. Проверить, не существует ли уже нужный класс, функция (утилита) или сервис. **Не дублируйте функциональность**.
3. Проверить существующие настройки в `config/settings.yaml`. Запрещено хардкодить то, что должно быть в конфиге.
4. Проверить модели. Если нужно новое поле, добавлять его в существующий `@dataclass`.

### Правила исследования проекта:
- Запрещено выполнять повторные исследования и парсить весь проект с нуля.
- Запрещено использовать конструкцию вида `python -c "..."` для рутинного исследования структуры.
- Если требуется сложная аналитика — используйте временные debug-скрипты, но **обязательно удаляйте их после завершения задачи**.
- Временные JSON-дампы не могут выступать в качестве "источника истины" — ориентируйтесь на работу реальных сервисов и API.

### 11. Правила принятия решений
Перед началом реализации любой задачи необходимо:
1. Прочитать техническое задание полностью.
2. Ознакомиться с `PROJECT_GUIDE.md`.
3. Определить затрагиваемые модули.
4. Проверить существующие публичные интерфейсы.
Запрещается писать код до завершения этих шагов.

### 12. Правило минимальных изменений
Любая задача решается минимальным количеством изменений.
**Запрещено:**
- рефакторить несвязанный код;
- менять архитектуру без необходимости;
- переименовывать существующие сущности без явной причины;
- изменять работающие сервисы, если задача их не касается.

### 13. Правило локализации
Запрещается исследовать несвязанные модули (Contract Engine, Schedule Tracker, Bitrix и т.д.), если ошибка локализована в одном конкретном модуле (например, Offers Engine).

### 14. Диагностика
Перед написанием диагностического кода определите, какая информация отсутствует и какой сервис может её предоставить. 
Запрещено создавать несколько диагностических способов для одной задачи. Используйте только один debug-скрипт.

### 15. Работа с логами
Сначала проверять логи (server log, journalctl, лог-файлы). Если причина ошибки там уже есть — дополнительное исследование через код не требуется.

### 16. Работа с Google Sheets
Структура листов считается известной после первого анализа. Повторный анализ запрещен, кроме случаев: изменения Spreadsheet ID/gid, сообщения пользователя об изменениях, признаков ошибки парсинга.

### 17. Работа с существующим кодом
Перед созданием новых сущностей (классов, функций, моделей) обязательно проверьте наличие аналогов. Дублирование запрещено.

### 18. Работа с временным кодом
Жизненный цикл: Создание → Использование → Удаление. После завершения задачи в проекте не должно оставаться debug-скриптов, временных JSON, закомментированного кода.

### 19. Обязательная самопроверка
Перед завершением задачи проверьте: реализацию всех требований ТЗ, минимальность изменений, удаление временного кода, обновление документации, прохождение тестов, отсутствие поломок в других модулях.

### 20. Главный принцип работы
Перед исследованием задавайте вопросы:
- Есть ли эта информация в `PROJECT_GUIDE.md`?
- Изучался ли этот участок ранее?
- Можно ли использовать существующий интерфейс?
Если ответ "да" хотя бы на один вопрос — повторное исследование выполнять **не следует**.

### 21. Использование Dependency Injection
Запрещается вручную конструировать зависимости существующих сервисов, если в проекте уже существует механизм их создания (Composition Root / Dependency Injection). Любая диагностика должна использовать те же объекты и тот же путь выполнения, что и рабочее приложение.
